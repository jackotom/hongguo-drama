## 用户方案评估

- [PR #129](https://github.com/jackotom/hongguo-drama/pull/129)：根因成立，已补明确的本地文件选择出口；自动授予低画质文件播放与固定画质约束存在差异，未直接合并。改用仅当前集、当前登记文件的人工选择，保留暂停进度及坏文件保护，并补齐画质操作撤销待定授权的竞态，Astra复审通过。
- [#95](https://github.com/jackotom/hongguo-drama/issues/95)：识别 ByteVC2 后使用 Librempeg、其他编码沿用现有工具，方向有效；项目已采用，无需重复移植。
- [#119 引用的 PR #72](https://github.com/zfdang/hongguo-open-player/pull/72)：核对变更后确认仍先完整写入输入，再使用 libx264 ultrafast/CRF25 与 AAC 编码。它增加兼容转换能力，不能证明免转码或更快。本项目保留现有 Apple Silicon 硬件 H.264 编码与音频复制，其余平台保持原软件路径。
- [#91](https://github.com/jackotom/hongguo-drama/issues/91)：每次新 App 取源使用独立匿名身份已在当前代码采用；不能再次用它解释或修复更早发生的注册失败。
- #91 按 expire_time 缓存的建议有减少重复请求的价值。当前只有短期成功结果缓存，正式采用前需覆盖服务端到期、安全余量、画质/降档键、强制重连、失败失效及流会话持有的片源；首次下载不同集数不会靠缓存加速。此优化未实现、未验证，不能当作 #127 或 #128 已根治。
- [#90](https://github.com/jackotom/hongguo-drama/issues/90)：CPU 软件解码已有历史用户成功反馈，当前桌面代码也保留；它处理特定解码兼容性，不修复本地文件拒用状态或注册网络。TV 暂不直接移植桌面解码器。
- 换节点、反复刷新和定时点击全部开始属于临时经验；没有据此自动改代理、关闭 TLS 校验或加入无限重试。

## 必须保留的验收边界

不能因单元检查通过宣称四台 TV 可用；不能用模拟字节声称真实视频解码通过。临时输出仍独占创建，只清理已取得归属的文件；不覆盖完成视频。未知的用户现场网络、首个解码失败原因、残留产生条件及真实阶段耗时继续明确列出，不以发版替代证据。
